# Phase 2 — remove redundant test cases

Compare cases pairwise (or cluster by asserted behavior):

1. **Exact / subsumed**: if A's assertions are a subset of B's and preconditions are equivalent, drop A; record under `dropped[]` with `reason: subsumed-by:<B.id>`.
2. **Same behavior, non-impactful data delta**: if two cases assert the same behavior and differ only by a factor value that does not change the outcome, keep the higher-risk one; drop the other (`reason: duplicate-behavior`).
3. **Instrumentation / observation-layer duplicate (MANDATORY)**: if two cases assert the **same guarantee** and differ only in **where or how it is observed** — e.g. one checks the browser Network tab (frontend) and another the backend API log / DB for the same "at most one performOrderReturn" guarantee — do not keep both. **Merge into one case asserting at both layers**: take the survivor, append the dropped case's distinct layer assertion to its `assertions[]`, union `covers[]`, and record the other under `dropped[]` with `reason: merged-observation-layer:<survivor.id>`. This turns S009/S011-style pairs into a single end-to-end-asserted case.
4. **Coverage safety check**: before dropping, confirm the survivor still carries every `covers[]` combination id and every **distinct** assertion the dropped case had (merge assertions into the survivor, not just `covers[]`). Never drop the only case covering a high-risk pair, a Negative, a Boundary value, or the only case covering a P0 factor value (priority carried from stage 1). When two cases are otherwise equivalent, keep the one touching the higher-priority (P0 > P1 > P2) factor.
   - **Polarity is not a shield against dedup.** A `Boundary`/`Negative` tag does not by itself make a case unique. If it asserts the *same guarantee* as another case and differs only by observation layer or a guard-invariant value, it is still a duplicate — merge per rule 3 and keep the stronger polarity on the survivor. Only protect a polarity when it is the **only** case exercising a genuinely distinct boundary/negative condition (an actual edge value or error path), not merely a different way of watching the same outcome.
5. Keep all `plan-derived` cases unless an exact duplicate exists.
